# 合同法律智能问答系统 —— 实施方案

## 一、项目定位

**选题**：面向中文合同/法律场景的多格式知识库问答系统
**技术特点**：多格式数据处理 + BM25/向量混合检索 + Qdrant 向量数据库 + LLM 生成

---

## 二、数据源方案（多格式组合）

| 格式 | 数据内容 | 来源 | 用途 |
|---|---|---|---|
| **PDF** | 《民法典》合同编全文 | 中国人大网/国务院官网公开PDF | 法条依据，条文粒度小，适合练习"按条/款切块" |
| **PDF** | 政府发布的合同示范文本（如《商品房买卖合同示范文本》《劳动合同示范文本》等） | 住建部、人社部等官网公开发布 | 真实合同结构，含条款编号、章节层级 |
| **DOCX** | 网络公开的通用合同模板（保密协议、租赁合同、买卖合同等 word 版范本） | 公开法律文书网站的免费模板 | 练习 docx 解析，格式比PDF更干净 |
| **XLSX** | 自建"合同条款风险对照表"：列包括 `条款类型`、`风险等级`、`常见违约情形`、`对应法条`、`案例编号` | 参考《民法典》和示范文本自己整理 20-30 行结构化数据 | 练习"表格型知识"的检索——这类数据不适合直接切文本块，要按行转成"一行一个知识点"的文本描述再入库 |
| （可选） | 裁判文书网公开的合同纠纷判决书 PDF | 中国裁判文书网 | 增加真实案例，但注意裁判文书网有反爬机制，建议手动下载几份，不建议写爬虫批量抓取 |

> 建议规模：法条 PDF 1份 + 示范文本 PDF 3-5份 + docx模板 3-5份 + 自建excel 1份，总量20个文档左右即可，重点不在"多"，在于"处理流程覆盖多格式"。

## 三、系统架构

```
┌─────────────┐
│  多格式数据源  │  PDF / DOCX / XLSX
└──────┬──────┘
       ↓
┌─────────────────────┐
│   解析层（按格式分发）  │
│  PDF → pdfplumber    │
│  DOCX → python-docx  │
│  XLSX → pandas/openpyxl │
└──────┬──────────────┘
       ↓
┌─────────────────────┐
│     切块（Chunking）  │
│  法条：按"第X条"切     │
│  合同模板：按章节/条款切 │
│  表格：按行转自然语言句子 │
└──────┬──────────────┘
       ↓
┌─────────────────────┐
│   向量化 + 稀疏编码    │
│  Dense: bge-large-zh │
│  Sparse: BM25/SPLADE │
└──────┬──────────────┘
       ↓
┌─────────────────────┐
│   Qdrant（存 dense+sparse）│
└──────┬──────────────┘
       ↓
┌─────────────────────┐
│  混合检索 + RRF融合 + (可选)rerank │
└──────┬──────────────┘
       ↓
┌─────────────────────┐
│  LLM生成（要求标注引用出处） │
└──────┬──────────────┘
       ↓
┌─────────────────────┐
│      前端问答界面      │
└─────────────────────┘
```

### 关于 BM25 + 向量混合检索的两种实现方式

**方式A（推荐给课程项目，简单可控）**
- 用 `rank_bm25` 库单独对全部chunk文本建一个BM25索引（存内存或本地文件即可）
- 用向量embedding单独在Qdrant里检索
- 两边各取 top-20，用 **RRF（Reciprocal Rank Fusion）** 公式融合排序：
  `score = Σ 1/(k + rank_i)`，k通常取60
- 优点：原理清晰，方便你在报告里解释"为什么融合"，出问题也好排查

**方式B（进阶，技术含量更高）**
- Qdrant 从1.10版本起原生支持**稀疏向量**（sparse vector），可以用 `fastembed` 库的BM25/SPLADE编码器，把稀疏向量和稠密向量**存进同一个collection**，一次查询同时返回两种召回结果，Qdrant自带 `Fusion.RRF` 融合方法
- 优点：架构更统一，是目前业界的主流做法
- 建议：先按方式A把流程跑通，再升级到方式B作为加分项

## 四、关键技术选型

| 模块 | 选型 | 说明 |
|---|---|---|
| PDF解析 | `pdfplumber` | 比PyPDF2对中文和表格支持更好；扫描件需加 `paddleocr` |
| DOCX解析 | `python-docx` | 按段落+样式（标题/正文）提取层级 |
| Excel解析 | `pandas` | 逐行转文本："【条款类型】保密条款 【风险等级】高 【常见违约情形】...《对应法条》第XX条" |
| 中文Embedding | `BAAI/bge-large-zh-v1.5` 或 `BAAI/bge-m3` | bge-m3 一个模型同时支持dense+sparse+多语言，适合方式B |
| 向量库 | `Qdrant`（docker本地部署） | 支持混合检索、payload过滤（按合同类型/文档来源筛选） |
| Rerank（可选） | `bge-reranker-v2-m3` | 对融合后的top-20做精排 |
| LLM | Claude / 通义千问 / GLM API 均可 | 中文法律场景建议选中文能力强的模型 |
| 前端 | Streamlit（快）或 Gradio | 课程项目优先选这个，省时间 |

## 五、详细实施步骤（建议按此顺序推进）

### 阶段0：环境搭建（0.5天）
1. `docker run -p 6333:6333 qdrant/qdrant` 本地起Qdrant
2. Python环境：`pip install qdrant-client fastembed rank_bm25 pdfplumber python-docx pandas openpyxl`
3. 准备好LLM API Key

### 阶段1：数据收集（0.5-1天）
1. 下载《民法典》合同编PDF、2-3份政府合同示范文本PDF
2. 找3-5份合同模板docx（保密协议、租赁合同等常见类型）
3. 手工整理一份 `合同条款风险对照表.xlsx`（20-30行，字段见上表）
4. 把文件按类型分文件夹存放：`data/pdf/`、`data/docx/`、`data/excel/`

### 阶段2：数据解析（1-1.5天）
1. 写三个独立的parser函数：`parse_pdf()`、`parse_docx()`、`parse_excel()`
2. 每个函数返回统一格式：`{"text": "...", "source_file": "...", "source_type": "pdf/docx/xlsx", "extra_meta": {...}}`
3. 重点：PDF解析时保留页码；docx解析时保留标题层级；excel解析时保留原始行号，方便溯源

### 阶段3：切块策略（1天）
1. 法条类PDF：用正则按"第X条"切分，每条一个chunk
2. 合同模板（PDF/docx）：按"一、二、三"或"第X条"等条款编号切分；没有编号的按段落+滑动窗口（如500字，overlap 50字）
3. Excel：不切块，一行转一个chunk（因为一行本身就是一个完整知识点）
4. 统一chunk结构：`{"chunk_id": "...", "text": "...", "metadata": {"source_type", "doc_name", "clause_no"/"page"/"row_no"}}`

### 阶段4：向量化与入库（1天）
1. 用bge模型把所有chunk转成dense向量
2. （如选方式B）同时用fastembed生成sparse向量
3. 创建Qdrant collection，设计payload字段（`source_type`, `doc_name`, `contract_type`），方便之后按条件过滤检索
4. 批量upsert入库

### 阶段5：检索模块（1-1.5天）
1. 实现BM25检索（rank_bm25，对文本分词用jieba）
2. 实现向量检索（Qdrant查询）
3. 实现RRF融合函数，输出融合后的top-k
4. （可选）加bge-reranker对融合结果精排

### 阶段6：生成模块（0.5-1天）
1. 设计prompt模板，明确要求：
   - 只根据检索到的内容回答，不要编造
   - 回答时标注引用来源（文档名+条款号/页码）
   - 如果检索内容不足以回答，要说明"未在知识库中找到相关依据"
2. 调用LLM API拼接生成

### 阶段7：前端（1天）
1. Streamlit搭建：输入框 + 答案展示区 + "引用来源"折叠展示（点开显示原文chunk）
2. 可加一个"按合同类型筛选"的下拉框，对应Qdrant的payload过滤

### 阶段8：评测（可选加分项，0.5-1天）
1. 自己手写10-15个测试问题+人工标注的"应该检索到的chunk"
2. 计算 Recall@5 / Recall@10，对比"只用BM25"、"只用向量"、"混合检索"三种方案的效果差异
3. 这一步能直接证明"为什么要做混合检索"，是报告里很有说服力的一节

### 阶段9：整理与汇报（0.5天）
1. 整理架构图、流程图
2. 准备2-3个演示问题（建议覆盖：法条查询类、合同条款风险类、表格数据查询类，正好对应三种数据格式）

## 六、总预估工时：约8-10天（业余时间可拉长到2-3周）

## 七、如果要进一步突出"混合检索"的价值，建议演示环节准备这样的问题
- 一个**关键词精确匹配**占优的问题（比如问具体某个条款编号）——体现BM25优势
- 一个**语义相似但用词不同**的问题（比如用"违约金怎么算"问一个措辞完全不同的条款）——体现向量检索优势
- 现场对比"只用BM25" vs "只用向量" vs "混合"三种结果，这是很好的答辩展示点
